# Next Windows release — acceptance checklist (2026-11-27)

Base: v1.1.4. Target proposed: v1.1.5. Work branch, not a stable release. All items require implementation and verification. Do not merge the temporary validation push trigger.

Failed downloads or invalid data return a specific error without falling back to default config. Existing same-source MMDB pending updates carry their receipts. Missing unused built-in datasets remain lazy. Automatic restart on this condition is not implemented; actual Windows mapped-file and parser integration need CI and native verification.

## Additional mandatory high-priority requirements (approved 2026-11-27)

- Unified UI system: centralize reusable titles, tabs, buttons, navigation, text/icon hover and focus treatment, semantic colors and material tokens. Reuse existing shared components rather than introducing parallel styling systems. Preserve accessibility, keyboard navigation and the approved geometry; cover light/dark modes and every full page/subpage.
- Material-aware semantic contrast: retain approved network hues, use text-only semantic emphasis independent of theme accent, and adapt luminance to the effective surface. Maintain WCAG AA 4.5:1 for ordinary text wherever the effective backdrop can be controlled; enforce a shared material luminance range if necessary to avoid indistinguishable colors on mid-grey. Do not introduce per-label colored backgrounds or claim to measure native DWM pixels from Flutter theme colors. Preserve labels/icons as redundant cues; verify real opaque/Mica/Mica Alt/Acrylic surfaces, stripes and custom settings, including hue separation and readability. Document native limitations.
- Single network statistics source: share lifecycle-managed Mihomo connection snapshots, true active TCP/UDP counts, traffic and existing probes across sidebar, dashboard, connections and diagnostics; preserve route and session semantics. Deduplicate concurrent reads, avoid polling from individual consumers, use bounded cadence, backpressure, error/stale state and restart/reconnect invalidation. Keep polling needed by service health independent from GUI visibility; no heavy automatic speed tests.
- Virtualized connection and log tables: reuse existing lazy lists where sufficient; avoid constructing or laying out all rows, preserve stable keys, scrolling, sorting, filtering, selection, copy and detail actions. Bound retained UI data without deleting configured on-disk log archives. Verify 1,000 and 10,000 representative connection/log rows, including rapid updates, with no overflow or excessive allocation.
- Change-driven rendering: avoid redundant rebuilds when equivalent snapshots arrive; use field-specific selectors, stable immutable state and throttled/coalesced updates where appropriate. Suspend nonessential hidden-page UI work and catch up on return without resetting services, losing records or suppressing real state changes. Test unchanged versus changed snapshots, visibility, reconnection and counter resets.
- Settings recovery: transactional/atomic persistent writes with safe flush and replace semantics on Windows, last-known-good validated recovery copy, corruption detection and deterministic fallback. Preserve existing preferences and unrelated fields; avoid overwriting the last valid copy with corrupt data, retain evidence and report recovery. Test interruption, invalid/truncated files, failed writes, permissions and concurrent updates; do not silently replace valid user data with defaults.
- Versioned settings migrations: idempotent, tested migration from v1.1.4 and supported legacy formats; retain per-key user overrides, profile ownership and managed locks, unknown fields and explicit false/zero/empty values; adopt new defaults only where appropriate. Cover upgrade/restart, malformed/old data, recovery and downgrade behavior without leaking credentials or modifying FlClashX settings.
- Release-to-release performance verification: establish a reproducible v1.1.4 baseline and compare the exact v1.1.5 candidate using matching Windows hardware/VM, build mode, settings and workload. Record idle/active CPU, working set/private memory, cold/warm startup, UI frame latency/scroll responsiveness and connection/log stress. Distinguish GUI from Mihomo/Zapret/Helper. Report distributions and meaningful regressions; investigate before publishing, do not invent measurements or numerical thresholds not yet established. Keep benchmark scripts/results reproducible; identify tests requiring physical Windows hardware.

Test live changes, reset, persistence and light/dark modes.
